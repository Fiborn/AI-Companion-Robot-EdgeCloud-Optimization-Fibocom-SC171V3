# 端云协同方案

> 对应作品：基于广和通 SC171V3 平台的 AI 陪伴桌面机器人与端云协同优化
> 硬件前提：SC171 开发套件 V3 —— 8 核 ARM v8（最高 2.7GHz）、13 TOPS 综合算力、Ubuntu 20.04 + Python 3.8 + ROS 2 + Fibo AI Stack

## 一、为什么要做端云协同

陪伴机器人如果只走云端大模型，会同时踩三个坑：

| 问题 | 纯云端方案的表现 |
| --- | --- |
| 响应时延 | 语音 → 上云 → ASR → LLM → TTS → 回传，链路长，体感"迟钝"（普遍 2.5–5 s） |
| 断网可用性 | 网络抖动或断网时机器人直接"变砖"，连"开灯""现在几点"都答不了 |
| 隐私 | 家庭环境的语音与图像全部上云，长期陪伴场景用户难以接受 |

只走端侧也不行：0.6–1.7B 的小模型知识面窄、多轮指代弱，复杂问题答不好，且会持续占用 NPU 与电量。

**结论：按意图分流——能本地闭环的绝不上云，需要理解深度的才走云。**

## 二、端云职责划分

| 能力 | 端侧（SC171 V3） | 云侧 |
| --- | --- | --- |
| 语音唤醒 / VAD | ✅ 本地常驻 | — |
| ASR / TTS | ✅ 本地轻量模型（首选） | 备选云端高精度识别 |
| 意图分类 | ✅ 小模型 / 规则引擎 | — |
| 设备控制（开灯 / 调音量 / 拍照） | ✅ Function Calling 本地执行 | — |
| 常见问答、闲聊、角色化人设 | ✅ 0.6–1.7B 本地 LLM | — |
| 复杂推理、知识问答、长文本 | — | ✅ 云端大模型（DeepSeek 等） |
| 长期记忆（≥10 轮对话历史） | ✅ 本地维护对话摘要与用户画像 | ✅ 云端持久化 + 跨设备同步 |
| 环境数据融合与阈值判定 | ✅ 传感器上报后本地判定 | ✅ 历史趋势与报表 |
| 视觉姿态检测 | ✅ Fibo AI Stack 部署的姿态模型 | 可选云端二次复核 |

## 三、分流策略

```text
                      ┌──────────────┐
        用户语音 ────▶ │  唤醒 + ASR   │  端侧
                      └──────┬───────┘
                             ▼
                      ┌──────────────┐
                      │   意图分类    │  端侧小模型 / 规则
                      └──┬────────┬──┘
                         │        │
          本地闭环类 ─────┘        └───── 深度理解类
     (设备控制 / 环境查询 /              (开放问答 / 复杂推理 /
      闲聊 / 时间天气缓存)                长文本 / 知识检索)
                 │                                  │
                 ▼                                  ▼
        ┌────────────────┐                 ┌────────────────┐
        │ 端侧 0.6–1.7B  │                 │   云端大模型    │
        │      LLM       │                 │  (OpenAI 兼容)  │
        └────────┬───────┘                 └────────┬───────┘
                 └──────────┬───────────────────────┘
                            ▼
                    ┌──────────────┐
                    │  TTS 播报 +   │  端侧
                    │  动作/灯效联动 │
                    └──────────────┘
```

**动态分流规则**（按优先级）：

1. 命中设备控制白名单（开灯 / 调音量 / 拍照 / 查环境数值）→ **强制本地**，不走网络。
2. 网络不可用或 RTT 连续 3 次超过阈值 → **全部降级到本地**，并语音告知"当前处于离线模式"。
3. 本地小模型置信度低于阈值（意图分类概率 < 0.6，或生成结果命中"我不知道"类拒答模板）→ **转云**。
4. 其余情况 → 按预设比例（如 7:3）在端侧闭环与云端之间调度，避免 NPU 长期满载。

## 四、时延预算

以"用户说完话 → 听到第一个音节"为端到端指标，目标 **≤ 2 s**：

| 环节 | 端侧路径 | 云端路径 |
| --- | --- | --- |
| VAD 断句 | 100 ms | 100 ms |
| ASR | 200–300 ms（本地流式） | 400–700 ms（上行 + 云端） |
| 意图分类 | 20 ms | — |
| LLM 首 token | 150–300 ms（本地小模型） | 500–1200 ms |
| TTS 首帧 | 150–250 ms（本地） | 300–500 ms |
| **合计** | **约 0.7–1.0 s** | **约 1.5–2.5 s** |

端侧路径稳定落在 2 s 以内，这正是"端云协同"最直观的收益点，也是答辩时最好量化的对比项。

## 五、与现有工程的衔接

现有代码处于**纯云端**状态，需要补端侧这一环：

| 现有实现 | 位置 | 现状 | 端云协同改造 |
| --- | --- | --- | --- |
| AI 对话 | `cloud/iot_platform/.../CompanionAiChatService.java` | 直接 POST 云端 OpenAI 兼容接口，串行等待，超时 30 s | 前置分流器：先本地判定，仅"深度理解类"才发起云端调用 |
| 模型配置 | `s_ai_model_config` 表 + `AiModelConfigController` | 单条 `active` 记录，切换后同步语音端 `.env` | 扩展为「端侧模型」+「云侧模型」两组配置，分别下发 |
| 配置同步 | `VoiceServerConfigService.java` | 写 `AI2/.env` 的 `OPENAI_BASE_URL` / `OPENAI_MODEL` 等 | 增加端侧推理服务的配置项（本地模型路径、NPU 线程数、置信度阈值） |
| 语音链路 | `xiaozhi-client` + `nuanxin-esp32-server` | 走云端大模型 | 加入端侧 ASR/LLM/TTS 节点，云端降级为可选后端 |
| 设备控制 | 自研二进制 TCP `PWM_SET` (0x0012) | 由 Web 后台下发 | 追加 Function Calling 本地触发通道，语音也能控灯 |

> 改造不涉及协议变更 —— 端侧闭环走的还是既有的 TCP 报文，只是触发源从 HTTP 变成了本地意图。

## 六、可作为答辩指标的对标项

广和通 AIoT 赛题公开的技术指标，可直接作为本作品的性能对标口径：

| 指标 | 目标值 |
| --- | --- |
| ASR + TTS 响应时延 | ≤ 2 s（优秀） |
| 端侧 LLM 参数量 | 0.6 – 1.7 B，本地推理 |
| 长期记忆 | ≥ 10 轮对话历史 |
| 多模态能力 | 语音 + 视觉（CV 模型推理）+ 环境传感器 |
| 工具调用 | Function Calling 对接天气、闹钟、设备控制等 |
